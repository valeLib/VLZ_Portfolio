Overview

Goblin TD is a tower defense game with a goblin worker management layer. Instead of passive automated towers, the player manages a living village of goblin workers who physically move through the world, construct structures, mine resources, and staff defense positions as stationed archers.

The game alternates between two phases: a build phase (construct structures, assign goblins, research technologies) and a defense phase (survive enemy waves). Victory requires surviving five waves without losing the central crystal.

The Design Decision That Defines the Game

In most tower defense games, towers are abstract slots. You place a tower, it fires. The “tower” is a number, not a thing.

Goblin TD makes goblins physical entities. They path to their assigned structure via NavMesh, they occupy visible slots, and during defense phases they appear as rotating archers on tower battlements. The mine doesn't produce gold — the three goblins inside the mine produce gold, proportional to how many there are.

This single design choice cascades into everything: the goblin population system, the training queue, the food economy that makes goblins a scarce resource, the visual controller that drives their animation state from assignment changes.

Architecture: Three Core Pillars

ScriptableObject Data Layer
All static configuration lives in ScriptableObjects: StructureData, EnemyData, WaveData, TechNodeBase. Game components read from these at runtime without storing copies. Balance changes require no recompilation — a critical architectural decision for a team project where multiple people are touching the same systems simultaneously.

Static Event Bus
GameEvents is a static class with one event per meaningful game action. Systems subscribe in OnEnable/Awake and unsubscribe in OnDestroy. No cross-references between managers — EconomyManager and WaveManager never know each other exist. This pattern made parallel development across team members possible without constant merge conflicts.

Modular Component Organization
~95 C# scripts organized under the GoblinTD namespace across 12 subfolders. Each system (construction, economy, combat, goblin agents) evolves independently without modifying shared contracts.

Key Systems

Technical Highlights

  • NavMesh pathfinding for all goblin agents, with per-agent configuration via GoblinVisualData ScriptableObjects

  • Object pooling for projectiles and enemies to avoid runtime allocation spikes during wave phases

  • Polymorphic tech nodes — FlagTechNode, MaterialUnlockTechNode, and StructureLevelUnlockTechNode each implement ApplyUnlock(), removing conditionals from the manager layer

  • RangeTriggerForwarder pattern — handles trigger callbacks on child colliders when the tower root has no Rigidbody (a Unity-specific problem requiring a specific architectural solution)

  • Animated construction sequence driven by a coroutine state machine, with optional skip for pre-placed scene structures

  • Progression persistence via ProgressionSaveSystem (PlayerPrefs), decoupled from scene loading logic in LevelManager

UI & HUD

Three-zone HUD: top resource bar, side build panel, bottom-contextual structure panel. All panels share parameterized AnimatorController clips for enter/exit transitions, minimizing animation asset count. Tooltip system driven by PointerEnter/PointerExit events with inspector-configurable content.

Audio split across two persistent managers: BackgroundMusicManager (menu / day / wave music) and UIButtonSoundManager (interface SFX via PlayOneShot). Combat audio handled locally per prefab.
